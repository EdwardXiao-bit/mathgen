# 03-协作规范

> 本项目允许**多个智能体并行工作**。本文件是并行协作的硬规则，不是建议。
> 与本文件冲突的临时做法一律无效；确需例外，先写进 [`00-决策记录.md`](00-决策记录.md)。

---

## 1. 为什么需要这份文件

智能体没有共享记忆：窗口会被摘要、会被替换。**只有磁盘上的文件是可靠记忆。** 并行协作只有三个真正会翻车的地方，本文件逐条封死：

| 失效模式 | 后果 | 本文件的对应机制 |
| --- | --- | --- |
| F1 两个人改同一个文件 | 互相覆盖，改动静默丢失 | §2 写域表 + §5 冲突处理 |
| F2 接口没冻结就各自实现 | 集成时字段名/语义对不上 | §6 接口冻结与变更流程 |
| F3 没人验证，靠「我做完了」 | 缺陷进入主干，返工成本翻倍 | §7 验证纪律 + §8 证据清单 |

**共享文档的「贡献—集成」约定**：`docs/06-测试方案.md` 的**唯一写者**是 `verify-m1`（它维护整份测试方案）；
**门禁作者**（如 `fe-teacher`）不为该文件落盘，而是把**可直接粘贴的小节文本**交给写者或 Lead 集成。
M4 期间 `fe-teacher` 曾直接写入 `docs/06` §9.5（当时 `verify-m1` 并未在改该文件，**没有发生实际碰撞**），
该内容已由 Lead 裁定**保留**并由 `verify-m1` 复核——**保留是因为内容有价值，不是因为规则允许**：
写域规则存在的目的是**避免两个人同时写同一文件**，不是给历史改稿判对错。**规则从下一轮开始收紧。**

**没有迁移目录**：建表走 `Base.metadata.create_all()`（`backend/app/db.py:74`），本项目**不使用 Alembic**。§2 原表列的 `backend/migrations/**` 是一个**不存在的路径**，已删除。

> 写域是**建议性约束**，靠自觉与 Lead 检查执行，不是文件锁。**看到写域外的文件，先停下问，不要顺手改。**

**对账规则（本节是用一次真实失效换来的）**：上表是**路径前缀**，**每一个前缀都必须在磁盘上真实存在**，且角色名必须与 `list_agents` 里的队友名逐字一致。
本表曾同时出现**四处**失效——写了**不存在的文件** `backend/app/schemas.py`、写了**不存在的目录** `backend/migrations/**`、写了**不存在的角色名** `be-api`（实际是 `be-paper`）、`verify` 的写域写成 `tests/e2e/**`（实际是 `backend/tests/e2e_ui/**` 等四个平级目录）。
**后果**：「按表找写域」会找到错的路径，而写域是并行协作唯一的防覆盖机制（失效模式 F1）——表失效等于机制失效，而且**失效是静默的**，没人会去验证一张表。
**规则**：新增/重命名目录时，**同一轮内**更新本表；发现表与磁盘不一致，**先改表再动手**。核对方法：逐个前缀核对磁盘存在性，角色名对 `list_agents`。
**这一核对已固化为自动化门禁**：`backend/tests/contract/test_write_domains.py`（随全量后端门禁一起跑）。它每次都做四件事——① 解析本表，每个**未标注**「尚未创建」的前缀必须在磁盘上真实存在（`/**`→目录、`/*`→非空目录、其余→文件或目录）；② 标注了「尚未创建」的前缀**必须确实不存在**；③ 角色名与钉住的名册 `EXPECTED_ROLES` **完全相等**（队友新增/改名要像改契约哈希一样刻意更新）；④ 两个角色的写域不得相等或互为前缀（§2 自己声明「一个路径同一时刻只有一个写者」）。门禁自身带 5 条负对照与 1 条正对照，防止判据恒真。
理由：一张只靠人记得去核对的表，迟早会再次漂移；而它上次漂移了**四处**都没人发现（与 V9「没有被验证过的约定，和被违反的约定一样不可靠」同源）。
**唯一的合法例外**：尚未 spawn 的角色，其写域**允许显式标注「（尚未创建）」**——**未标注**的不存在路径一律按失效处理。

## 3. 任务生命周期

```
待办 ──认领──> 实现中 ──自测通过──> 待验收 ──Lead 验收──> 已验收
                    │                     │
                    └──── 阻塞 ───────────┴──打回──> 实现中
```

规则：

1. **先登记再动手**：任何改动前，任务必须在 [`05-任务板.md`](05-任务板.md) 中存在，且含写域、依赖、验收标准三要素。
2. **认领即声明**：认领时把状态改为「实现中」并写上自己的角色名。同一任务不并发认领。
3. **依赖未完成不得开工**：任务卡列了 `依赖` 就先等；抢跑出来的代码在集成时基本要重写。
4. **自测通过才提交验收**：提交时必须附 §8 证据清单，缺证据的验收请求直接打回。
5. **打回要写原因**：不是「不行」，而是「哪条验收标准、观察到什么、期望什么」。

## 4. 交接协议（Handoff）

会话切换、角色换手、任务中断时，交接内容**必须**包含下面六项。少一项就等于没交接：

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | 任务 ID | 对应 `05-任务板.md` 的编号 |
| 2 | 改动文件清单 | 具体路径，不用「相关文件」这种说法 |
| 3 | 验证命令 | **可直接复制执行**的命令 |
| 4 | 原始输出 | 命令的真实输出（截取关键行），不是转述 |
| 5 | 未完成 / 遗留 | 已知的坑、TODO、未覆盖的分支 |
| 6 | 是否触碰冻结契约 | 若触碰，附决策记录编号 |

**反例（等于没交接）**：

> 「出题引擎已经写好了，功能正常，测试通过。」

**正例**：

> 任务 T-M1-01。改动：`backend/app/engine/{types,ranges,builders}.py`（新增）。
> 验证：`uv run pytest backend/tests/engine -q` → `18 passed in 0.42s`。
> 未完成：R6（四位数加减）的退位约束尚未覆盖，留 TODO 在 `builders.py:214`。
> 未触碰冻结契约。

## 5. 写域冲突处理

| 场景 | 处理 |
| --- | --- |
| 需要改他人写域内的文件 | 在任务板登记「跨域申请」，说明原因与改动范围 → **Lead 裁决** → 串行执行（前一个写者完成后再动） |
| 需要改共享只读区 | 同上，且必须同步：改 `01`/`02` 后**重新生成 Word**（D37） |
| 需要改 Lead 独占区 | 只能向 Lead 提交变更内容，由 Lead 落盘 |
| 发现两处实现矛盾 | **停下来**，在决策记录登记待决问题，Lead 裁决后再继续；不要两边同时改 |
| 紧急修复 | 允许先行修复，但必须在同一轮内补登记任务卡与证据 |

**永远不要**为了「让代码跑起来」而修改别人写域里的文件——这是本项目最容易发生的静默破坏。

## 6. 接口冻结与变更

- 接口的**唯一权威来源**是 [`04-接口契约.md`](04-接口契约.md)。`02-技术设计.md` 中的对应章节是设计说明；**两者冲突时以契约文件为准**，并同步回写 `02`。
- 契约中每一项标注状态：**冻结** / **草案**。草案可以边做边议，冻结项一个字都不能顺手改。
- 变更流程（**四步，缺一不可**）：

```
① 提案：在 00-决策记录.md 新增决策（D 编号），写明动机与影响面
② 定稿：更新 04-接口契约.md，提升版本号
③ 通知：在任务板给所有下游任务加备注
④ 同步：下游按新契约改完，并在证据清单里注明「已同步契约 vX」
```

### 6.1 功能增删 / 变更必须同步的文档（**D79**）

**「接口变更」只是这几类变更里最容易想起来的一种。** 新增或改动一个**功能**（哪怕不动接口），
同样必须在这一轮内把下面这些落盘——**不是"有空再补"，是同一个提交里**：

| 文档 | 什么时候必须动 | 谁写 |
| --- | --- | --- |
| `docs/00-决策记录.md` | **任何**功能增删 / 口径变化，新增 D 编号。这是**修改记录**，也是唯一的事实来源 | Lead 裁决后 Lead 写 |
| `docs/01-需求分析.md` | 新增 / 删除 / 改变一条**用户可见的功能**（FR 表） | 共享只读区（Lead 或经裁决） |
| `docs/02-技术设计.md` | 动了**表结构 / 数据模型 / 模块划分**（含新增列） | 共享只读区（Lead 或经裁决） |
| `docs/04-接口契约.md` | 动了**接口**（路由、字段、错误码、语义） | Lead 独占 |
| `docs/05-任务板.md` | **总是**——新任务、状态变化、来源说明 | Lead 独占 |
| `docs/06-测试方案.md` | 新增验收判据 / 门禁 | verify-m1 |
| `docs/07-设计规范.md` | 新增**组件**或新的**必守交互约定**（已有约定覆盖则不动） | Lead 独占 |
| `docs/word/**` | **不要求即时更新**（D37）——Word 由上述 md 生成，**最后阶段统一重生成** | docs-build |

**判定口径**：
- 「用户能看见的功能变了」→ `01` 必动；「数据结构变了」→ `02` 必动；**两者都变了就两份都动**。
- 想不清要不要动时**倾向动**：文档多写一句的成本，远低于最后写课程文档时发现「这功能哪来的」。
- **Word 可以晚，md 不能晚**：Word 是 md 的产物，md 及时更新就等于 Word 最终正确；
  反过来，md 拖到最后补，就等于让「修改记录」变成「事后回忆」。

### 6.2 这条规则为什么必须存在（实测，不是推演）

2026-10-15 用户问「功能的更改和增删是否落实到了项目文档中」。**审计结果是不完整的**：

- 新增 D78（卷库归档 / 删除）时，Lead 更新了 `00` / `04` / `05` / `03`，
  **漏了 `01`**（FR 表里没有「归档 / 删除」这条功能）与 **`02`**（`CREATE TABLE paper` 里没有 `archived_at`）。
- 更严重的是：**`02` 的 `attempt` 表连 D76 加的 `attempt_uuid` 都没有**——那是 M4 期间就漏的。
  也就是说这不是一次疏忽，而是**规则没覆盖**：`03` §6 的流程只管「接口变更」，只管 `04`，
  **没有任何一条要求同步 `01` / `02`**，也没有任何机器判据。

**根因与 V13 是同一条**：靠人记得去同步的约定，迟早会漂移，**而且漂移是静默的**——
没有任何东西会因为 `02` 少一列而变红。所以除了上面这张清单，**能机器对账的必须机器对账**：
`docs/02` 里的建表语句 ↔ `backend/app/models.py` 的列，应有一条门禁逐列比对（见任务板 T-M4-17）。
**写下清单只解决了"知道要做什么"；判据才解决"没做会被发现"。**

- **禁止**「顺手改一下接口」：字段改名、默认值变化、可空性变化，都属于破坏性变更，必须走流程。

## 7. 验证纪律

> **没有人能自证完工。** 「我做完了」不是证据，可复现的命令与原始输出才是。

| 规则 | 说明 |
| --- | --- |
| V1 | 每个任务的完成都必须跑 [`06-测试方案.md`](06-测试方案.md) 中该模块的**门禁测试**，并贴出原始输出 |
| V2 | 涉及冻结契约的改动，必须跑**契约测试**（字段名、类型、可空性） |
| V3 | 关键模块（出题引擎、判分、卷状态机）由 **verify 角色独立复跑**，不能只有写者自己的测试 |
| V4 | Lead 在宣布里程碑完成前，必须**自己再跑一次**端到端验收，并保留命令与输出 |
| V5 | 可视化产物（卷面、PDF、Word）必须**实际渲染出来看过**，不能只看代码 |
| V6 | 性能类结论（NFR-4）必须给**实测数字**，不接受「应该很快」 |
| V7 | **跑门禁期间不得落盘**：全量门禁运行窗口内，**任何写者都不得修改实现或测试文件**。跨写者并行无法完全避免时，必须用**运行前后哈希夹逼**（跑前跑后各存一次 `backend/app/**` 的 sha256 清单）标记出「窗口内内容被改动」的无效运行并**排除该次结论** |
| V8 | 门禁结论**只对「运行窗口内内容不变」成立**：验收报告须写明运行窗口与哈希夹逼结果（T1 == T3） |
| V9 | **任何新断言必须能失败**：新增或修改判据时，必须举出一个**能让它失败的输入（负对照）**，并在报告里给出该对照的实测输出。**恒真断言不算判据**——例如依赖 CSS 初值（`outline-width` 初值就是 `medium`=3px）、`> 0`、`!= null`、`?? 0` 兜底后比较等。<br>**V9.1 负对照要留在仓库里**：负对照不能只是一次性跑过的输出——**必须是一个可以随时重跑的产物**（常驻门禁步骤，或仓库内可执行的脚本）。理由：报告会过期，脚本不会；**别人必须能复核你的判据真的会红**。<br>**V9.2 负对照本身也要被验证**：必须确认它**真的制造了失败条件**。实测教训——用 `width:100%` 注入去重现 A9 压扁**无效**（iframe 内容视口已是 793.7，`100%` 解析出来还是 793.7），必须显式给一个比 A4 窄的固定宽度才重现。否则会得到一个假的「判据有效」结论 |
| V10 | **断言必须命中所声称的对象**：一处断言若它**命中的元素可能不是它想操作的元素**，它的通过**不构成证据**。<br>**失败模式**：子串/模糊选择器会命中一个**更靠前、语义无关**的元素——实测（task-26）`page.click("text=开始答题")` 命中说明文字 `<p class="st-lead">…再开始答题。</p>` 而不是按钮，于是整条链路"根本没发生"却有一半断言是绿的。<br>**修法不是把字符串写长**（那只是提高巧合成本，没有消除它），而是换成**语义/结构选择器**：`get_by_role("button", name="开始答题", exact=True)`、`form button[type=submit]`。**V10 与 V9 同族但方向相反**：V9 管「断言抓不住东西」，V10 管「断言抓住了别的东西」 |
| V11 | **判据必须对它要区分的两种状态给出不同结论**（分辨力）。一条**恒红**的断言与一条恒真的断言**一样没有信息量**：后者让人以为问题被守住了，前者让人去修一个不存在的问题。<br>**实测（task-24）**：`{getattr(route, "path", None) for route in client.app.routes}` 用来断言「学生端 4 条路径已装配」。FastAPI **0.143.0**（`starlette 1.8.0`）的 `include_router` **不再把子路由摊平进 `app.routes`**，而是存成 `_IncludedRouter`（其 `path` 为 `None`）。于是装配前/装配后得到的是**完全相同的集合**：`{None, '/redoc', '/docs', '/docs/oauth2-redirect', '/openapi.json'}`。该断言无法区分它要区分的两种世界——**它不是在报警，它是在制造假警报**。<br>**操作口径**：写断言后自问「满足条件的世界里它会绿吗？」——只跑负对照不够，**正对照同样必须存在**（V9.2 的对偶）。**首选不依赖框架内部结构的判据**（例如直接发请求断言 `status_code != 404`），它既更难写错，本身也就是"真机可用"的证据 |
| V12 | **覆盖面必须被证明"扫到的是它声称的对象"**。三类静默失明，任何一类都能让门禁打印 PASS：<br>**(a) 按名字排除**：实测（task-27）`verify-contract.py` 的裸 `/api` 判据排除条件写成 `if ts_file.name == "api.ts": continue`，而**师生两端各有一个 `api.ts`** → `src/student/api.ts` 的 4 处裸路径被静默跳过，判据照样 PASS。**排除条件按"我以为它叫什么"写，就等于没排除；必须按路径写**。<br>**(b) 扫描对象是另一个应用**：实测（task-27）`verify-server.mjs` 的 catch 分支一律回落 `dist/index.html` → `/student/**` 实际拿到**老师端**应用。**任何"扫学生端"的判据都会静默扫成老师端并全绿**，而且**加得越多绿得越彻底**。<br>**(c) 路由存在但落进空壳**：页面在但选择器落空，判据对着空集合比大小。<br>**操作口径（三者缺一不可）**：① **注入已知标记进目标，断言被抓到**（覆盖面对照）；② **断言所服务/所扫描对象的身份**（如 `/student` 必须引用 `student-*` 而非 `main-*`）；③ **哨兵会自己过期**——把「已知缺陷当前存在」写成断言，缺陷修好后哨兵自己变红，逼人撤哨兵，比把缺陷记在报告里强 |
| V13 | **宣布"预期红/预期绿"之前，必须先核对判据的输入集合**。「预期」本身也是一条断言，**它同样要有分辨力**。<br>**实测（D78，M4.x）**：Lead 在 `docs/04` §9 加了一行 `PAPER_HAS_ATTEMPTS`，然后要求 be-paper「先确认双向对账判据真的红了，如果它是绿的说明判据坏了」。**判据没红——而它也没坏**：`assert_error_codes_agree(ERROR_HTTP_STATUS, CONTRACT_ERROR_CODES)` 的两个参数**都是机器侧**（实现映射表 ↔ 测试侧硬编码副本），`docs/04` **根本不在它的输入里**。全仓 `backend/**` 对 `docs/04` 的 32 处引用**全是 docstring／注释／报告文字，没有一处是读文件解析** → **「文档 → 副本」这一步是纯手工誊抄，没有任何自动探测器**。<br>**教训**：一条判据的输入集合**不会写在它的名字里**。一条叫「契约一致性」的判据，听起来当然该管文档——而它从没读过文档。**说"它应该会红"之前，先去它的输入里找一找你改的那个东西在不在；不在，它红不了，而且这不是它的错。**<br>**操作口径**：① 把「预期红／预期绿」当成一条待验证的断言来对待（V11 对它的期望同样成立：**两种世界都要有具体输入**）；② 发现输入缺失时，补的是**输入**（把 `docs/04` 读进来做三方对账），而不是要求下游「更仔细地誊抄」——**手工同步正是那种会把差异藏起来的机制** |

> **V9 是 M3.5 用两次真实教训换来的**：
> ① **A9 缺陷穿过了 8 条门禁**——因为没有一条断言量到"纸里面"（A1 管颜色、A2 管组件状态、
> A4 管纸面**容器**比例、A7 管浮动层几何、A8 管不溢出）；
> ② 更严重的是，为修 A9 而新加的那条"**功能断言**"本身就是恒真的：
> `(outlineWidth ?? 0) > 0` —— 而 `outline-width` 的 CSS 初值就是 `medium` = 3px，
> **未聚焦的元素同样读到 `none` + `3px`**，所以它**永远不会失败**，也就证明不了它声称的"焦点环生效"。
> 当时 Lead 看到"从规则存在升级为功能断言"的说法就接受了，**没有要求给出能让它失败的输入**——这是 Lead 的失职。
> **判据不是"看起来更严"就更好；必须证明它抓得住东西。** 一个抓不住东西的判据比没有判据更危险：
> 它会让所有人以为这件事已经被守住了。

> **V10 是 M4 期间用一次"绿得侥幸"换来的**（task-26）：学生端探针第一版 **55/55 全绿**，
> 但其中 **7 处点击用的是 `text=` 子串选择器**（`开始`、`自主练习`、`下一题`、`交卷`…），
> 它们**碰巧**命中了正确元素。等补上「全新设备直接扫卷」这条新流程时，同样的写法命中了正文
> 而不是按钮，链路整条没发生才暴露出来。**绿得对，不等于绿得结实**——把 7 处换成语义选择器后
> 重跑的 64/64 才算数。

> **V11 是 M4 装配阶段用一次"恒红"换来的**：`main.py` 装配学生端路由前，护栏红是对的；
> **装配好之后它照样红**——同一份代码在"装配了"和"没装配"两种世界里给出**同一个集合**，
> 说明它从来没有在观测装配。真正的证据来自另一条**行为**断言（`/openapi.json` 里 4 条路径齐）。
> **判据的价值在于分辨力，不在于它有多严格。**

> **V12 是 M4 期间"覆盖面看着有、其实没有"换来的**（task-27）：这一轮发现的**两个**缺陷都不是
> "没覆盖"，而是"**覆盖了但判据抓不住**"——一个按**文件名**排除掉了师生同名的 `api.ts`，
> 一个让 `/student/**` **回落成了老师端应用**。两者的共同点：**它们都会打印 PASS**。
> 因此新增覆盖面时，**"我加了"不等于"我扫到了"**——必须有一条断言专门证明覆盖面是活的。

**已知测量陷阱**：本机 LibreOffice Kit 的 `docx → PNG` 光栅会把版心右移 1.53cm，看起来像排版溢出。**版式验收必须走 `docx → PDF → PNG`**。详见 `AGENTS.md`。

> **V7/V8 是 M3 期间用真实代价换来的**（D66）。当时两次「偶发失败」被当成测试不稳或产品缺陷排查：
> 一次 3 条红、一次 `PdfiumError: Data format error`。真因是 `backend/app/export/pdf.py`
> 在门禁运行窗口内被改写，失败全部指向**写入中间态**——
> `IndentationError (pdf.py:139)`、`ModuleNotFoundError: app.export.pdf`、`NameError: _forensic_capture`；
> 该文件 mtime 正落在窗口内；**哈希夹逼显示「窗口内内容未变的运行全绿、被改的运行必红」**。
> **代价**：两位智能体各花了一轮去追一个并不存在的缺陷。
> **教训**：一个「看起来像被测代码有问题」的红，也可能是**观测过程本身被污染**——先怀疑过程，再怀疑产品。
