## 1. 设计目标与约束

### 1.1 从需求继承的硬约束

| 编号 | 约束 | 对设计的影响 |
| --- | --- | --- |
| NFR-1 | 老师本机 / 教室内网机器运行，学生端局域网扫码访问，无公网 | 单进程部署；**不做 HTTPS、不做域名、不做云**；必须自动探测局域网 IP 并生成二维码 |
| NFR-2 | 本地 SQLite 单文件，数据不离开本机 | 不用任何外部数据库；备份 = 复制一个文件 |
| NFR-4 | 生成 20–50 题 1 秒内返回 | 出题必须是**纯内存计算**，不落库、不远程调用 |
| NFR-5 | 打印精确 A4 分页，题目不被跨页截断 | 渲染必须是**受控 HTML + CSS**，不能依赖不可控的第三方排版 |
| NFR-9 | 模式 A 完全无网可用 | 前端资源本地打包（无 CDN）；出题与导出全部在本地进程完成 |

### 1.2 设计原则

1. **快照优先于重算**：卷子一旦生成，题目内容以「快照」落库，不靠重新跑引擎还原（理由见 §4）。
2. **单一渲染真相源**：屏幕预览、打印、PDF 用同一份 HTML（理由见 §9）。
3. **引擎纯函数化**：出题引擎 `(config, seed) → questions`，无副作用、无 I/O，便于测试与复现。
4. **两端口径分家**：老师端与学生端共享后端与领域层，但界面、路由、依赖完全分开，学生端不加载任何老师端代码。

## 2. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端语言 | **Python 3.12** | D18 |
| Web 框架 | **FastAPI + Uvicorn** | 异步、自带 OpenAPI 文档便于联调；静态文件托管一并解决 |
| ORM / 迁移 | **SQLAlchemy 2.x + Alembic** | 表结构会随 DQ 演进，需要迁移能力 |
| 数据库 | **SQLite（WAL 模式）** | NFR-2；WAL 支持读写并发，够数十名学生用 |
| 出题引擎 | 纯 Python 自研模块 | 需求是小学数学特定约束，通用表达式库反而更难控 |
| PDF 导出 | **Playwright（Chromium）打印 HTML** | 与屏幕预览、浏览器打印共用同一份 HTML，从根上消除排版差异 |
| Word 导出 | **python-docx** | 唯一成熟的 .docx 生成库；需求 D8 明确要「可二次编辑」 |
| 二维码 | **qrcode + Pillow** | 局域网 URL 转二维码 |
| 前端 | **React 18 + TypeScript + Vite** | D18 |
| 前端状态 | **TanStack Query + 少量 zustand** | 服务端状态用 Query，本地排版参数用 zustand |
| 样式 | 原生 CSS + CSS 变量 | 排版参数（D30）需要变成 CSS 变量实时驱动，上 UI 框架反而碍事 |
| 测试 | pytest（后端）、Vitest（前端）、Playwright（端到端） | Playwright 已因 PDF 引入，复用做端到端最划算 |

> 选型说明：PDF 走 Playwright 而不是 `weasyprint` / `reportlab`，是一个**关键决策**——它让「预览 = 打印 = PDF」三者天然一致（NFR-5）。代价是分发体积增加约 150MB（Chromium），对个人自用场景可接受。

## 4. 核心设计一：卷的状态模型（D26 + D27 逼出来的）

### 4.1 问题

D26（生成后可删题换题）与 D27（卷库）把「卷」从**一次性中间结果**变成了**要持久化、可编辑、可复现的实体**。三者会互相打架：

- 老师改了题，但已经有学生做过了 → 那份成绩还对不对得上？
- 卷库存的是配置还是题目？存配置的话，引擎一升级，历史卷就变样了。
- 「复现」到底复现什么——同一套题，还是同配置的另一套题？

### 4.2 方案：快照 + 状态机

**（a）题目存快照，不存「重算配方」**

`paper_item` 保存题目的**完整快照**（题干、答案、脱式过程、难度、考点）。卷库打开时直接读快照，**不重新跑引擎**。

理由：引擎是会演进的（新增题型、修正算法、调整难度评分）。若历史卷靠重算，老师上学期的卷子就会在升级后悄悄变样——对老师而言这是数据损坏。

`paper.seed` 与 `paper.config` 仍然保存，但用途变成：**再生成一套同配置的题**、**审计与排错**，而不是还原原卷。

**（b）卷有状态，发布即冻结**

```
        ┌──────────┐   POST /publish    ┌────────────┐
生成 →  │  draft   │ ─────────────────► │ published  │
        │ 可删题   │                    │ 只读、有卷号│
        │ 可换题   │ ◄───────────────── │ 学生可做    │
        └──────────┘   不可逆（改题须   └────────────┘
                       另存为新卷）
```

| 状态 | 可编辑 | 学生可做 | 有卷号 |
| --- | --- | --- | --- |
| `draft` | 是（删题 / 换题） | 否 | 否 |
| `published` | **否** | 是（凭卷号或二维码） | 是 |

**发布后再想改题怎么办**（**已确认为 D32**）：走「另存为新版本」——复制快照成一张新 draft 卷，改完重新发布，得到新卷号。旧卷与其成绩**永久保留**，历史成绩不会因为改题而失真。

这条规则同时解决了 FR-T12（逐题对错明细）的可靠性问题：成绩永远能对应到当时那份确切的卷面。

**（c）删除题目不改变题号**

删题后**不重排题号**是不行的（卷面会有空号）。采用：删除 → 该 seq 从卷面移除 → **后续题号前移**，并在 `edit_log` 记一条（`deleted seq=N`）。因此同一张 draft 卷在编辑过程中，题号会变化——这是可接受的，因为 draft 不会有学生成绩产生。

### 4.3 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 只存 `(seed, config)`，用时重算 | 引擎升级会让历史卷变样，等于数据损坏 |
| 发布后允许直接改题 | 已产生的成绩无法解释，FR-T12 的明细会自相矛盾 |
| 每次改题生成新卷号 | 老师改 5 道题就得到 5 个卷号，卷库爆炸 |

## 5. 数据模型

### 5.1 实体关系

```
paper 1───n paper_item          （卷面题目快照）
paper 1───n attempt             （这套卷被做过的若干次）
student 1───n attempt           （同一学生的若干次练习）
attempt 1───n attempt_item      （逐题作答，支撑 FR-T12）
```

**边界说明**：`attempt.paper_id` 允许为 NULL——学生自主练习（FR-S3）没有卷，题目快照存在 `attempt.config_snapshot` 与 `attempt_item` 里。

### 5.2 表结构

```sql
-- 卷
CREATE TABLE paper (
  id            INTEGER PRIMARY KEY,
  code          TEXT UNIQUE,           -- 卷号 YYMM-NNNN（D34），draft 阶段为 NULL
  title         TEXT NOT NULL,
  status        TEXT NOT NULL,         -- draft | published
  seed          INTEGER NOT NULL,      -- 复现与再生成用
  config_json   TEXT NOT NULL,         -- GenerateConfig 快照
  layout_json   TEXT NOT NULL,         -- LayoutParams 快照（D30 六项）
  answer_layout TEXT NOT NULL,         -- 答案版：分页 / 是否含过程（D20）
  created_at    TEXT NOT NULL,
  published_at  TEXT
);

-- 卷面题目（快照，不重算）
CREATE TABLE paper_item (
  id          INTEGER PRIMARY KEY,
  paper_id    INTEGER NOT NULL REFERENCES paper(id) ON DELETE CASCADE,
  seq         INTEGER NOT NULL,        -- 卷面题号，删除后前移
  payload     TEXT NOT NULL,           -- Question 的 JSON 快照
  origin      TEXT NOT NULL,           -- generated | regenerated | ...
  UNIQUE(paper_id, seq)
);

-- 编辑日志（审计与排错）
CREATE TABLE edit_log (
  id         INTEGER PRIMARY KEY,
  paper_id   INTEGER NOT NULL REFERENCES paper(id),
  action     TEXT NOT NULL,            -- delete | regenerate
  seq        INTEGER,
  at         TEXT NOT NULL
);

-- 学生（姓名 + 学号，D35 修订 D12）
CREATE TABLE student (
  id         INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,
  student_no TEXT NOT NULL,            -- 学号，必填（D41）；仅用于区分同名
  created_at TEXT NOT NULL,
  UNIQUE(name, student_no)             -- 同名靠学号区分
);

-- 一次练习
CREATE TABLE attempt (
  id            INTEGER PRIMARY KEY,
  student_id    INTEGER NOT NULL REFERENCES student(id),
  paper_id      INTEGER REFERENCES paper(id),   -- NULL = 自主练习
  config_json   TEXT,                           -- 自主练习的配置快照
  total         INTEGER NOT NULL,
  correct       INTEGER NOT NULL,
  duration_ms   INTEGER NOT NULL,               -- FR-S6 用时
  submitted_at  TEXT NOT NULL
);

-- 逐题作答（FR-T12 / FR-S8）
CREATE TABLE attempt_item (
  id             INTEGER PRIMARY KEY,
  attempt_id     INTEGER NOT NULL REFERENCES attempt(id) ON DELETE CASCADE,
  seq            INTEGER NOT NULL,
  payload        TEXT NOT NULL,        -- 题目快照（含正确答案与过程）
  student_answer TEXT,
  is_correct     INTEGER NOT NULL,
  UNIQUE(attempt_id, seq)
);

CREATE INDEX idx_attempt_paper   ON attempt(paper_id);
CREATE INDEX idx_attempt_student ON attempt(student_id);
```

**关键取舍**：`attempt_item` 冗余保存题目快照，而不是只存 `paper_item_id`。这样即使卷被删、引擎升级、或该次是自主练习，历史成绩依然可完整还原——这是 FR-T12「学生答案是什么」能长期成立的前提。

## 6. 出题引擎设计

### 6.1 接口

```python
@dataclass(frozen=True)
class GenerateConfig:
    ops: set[Op]                      # ADD SUB MUL DIV        (FR-E1)
    ranges: list[RangeId]             # R1..R7                 (FR-E2)
    max_value: int | None             # R7 自定义上限          (FR-E3)
    require_carry: bool = False       # 进位                   (FR-E4)
    require_borrow: bool = False      # 退位
    exact_division: bool = False      # 必须整除
    allow_remainder: bool = False     # 允许余数
    parentheses: bool = False         # 含括号
    question_type: QuestionType       # ORAL | STEPWISE | FILL  (FR-E5/D17)
    count: int = 20                   # FR-E6

@dataclass(frozen=True)
class Question:
    expr: str            # "37 + 45"  或  "(12 + 8) ÷ 4"
    display: str         # 卷面展示形态，填空题含 □
    answer: str          # 标准答案（已规范化）
    steps: list[str]     # 脱式逐步过程 (FR-E12)
    difficulty: int      # 1..5 (FR-E10)
    tags: list[str]      # 考点标签 (FR-E11)
    signature: str       # 去重签名 (FR-E7)

def generate(config: GenerateConfig, seed: int) -> list[Question]: ...  # FR-E8
def regenerate_one(config, seed, seq, existing: list[Question]) -> Question: ...  # FR-E9
```

### 6.2 生成策略：构造式 + 约束回溯

不做「随机出算式再筛」，而是**按约束反向构造**，这样约束天然满足、无需重试风暴：

| 类型 | 构造方式 |
| --- | --- |
| 加法 | 按档位采样两个操作数，检查位数 / 上限 / 进位要求（进位与否决定个位和是否 ≥10） |
| 减法 | 先定结果与被减数，再反推减数，天然保证非负；退位由个位比较决定 |
| 乘法 | 按档位选择「一位数 × 两位数」等组合，保证结果在范围内 |
| 除法 | **先定除数与商，再相乘得被除数**——整除约束因此永远成立；有余数时再加一个小于除数的余数 |
| 脱式 / 混合 | 先建表达式树（运算符 + 括号结构），后序遍历求值，同时产出逐步过程 |
| 填空 | 生成基础题后按位置挖空（结果 / 加数 / 因数），答案即挖掉的数 |

约束冲突时（如「100 以内 + 必须进位」与题量过大）采用**有限次回溯 + 明确报错**，而不是无限重试。错误信息返回给老师端提示「当前约束组合可出的题不足」。

### 6.3 去重（FR-E7）

`signature` = 题干规范化后的字符串：去空格、统一运算符、**交换律等价归一**
（`3+5` 与 `5+3`、`2×6` 与 `6×2` 视为同一签名——否则低档位题量会大量重复）。

### 6.4 难度评分（FR-E10）

规则打分，可解释、可测试：

```
difficulty = 1
  + 位数贡献（操作数最大位数 - 1）
  + 进位/退位次数
  + 运算步数（脱式超出 1 步的部分）
  + 含括号 +1
  + 有余数除法 +1
规整到 1..5
```

### 6.5 判分（FR-S7）

- 归一化：去首尾空格、全角转半角、`÷`/`/` 统一、中文括号统一。
- 数值比较用 `Decimal`（避免浮点误差；整数四则下更稳）。
- 有余数除法接受两种合法写法（`7 余 2` / `7…2`），是否要求写余数由配置决定。
- 脱式题**判最终答案**，过程用于答案版展示与老师讲评，不参与自动判分（过程是否规范无法可靠自动判定——此处明确不做）。

| POST | `/api/student/practice` | 自主练习：传 config + 题量 → 返回题目 | FR-S3 |

**安全要点**：`GET /api/student/paper/{code}` 的响应体**必须剔除 `answer` 与 `steps`**。学生端拿不到答案，判分在服务端做。这是一处很容易写漏、又必须写对的边界，会加一条自动化测试守住。

## 8. 前端设计

### 8.1 路由与页面

| 端 | 路由 | 页面 |
| --- | --- | --- |
| 老师 | `/teacher` | 出题配置（六维表单） |
| 老师 | `/teacher/paper/:id` | 预览与改题 + 右侧排版面板（6 项，实时生效） |
| 老师 | `/teacher/library` | 卷库 |
| 老师 | `/teacher/paper/:id/publish` | 发卷（二维码 + 卷号同屏，D23） |

| 学生 | `/student` | 入口：输姓名 + 学号 + 两个入口（自主练习 / 输卷号） |

| 学生 | `/student/result` | 结果：得分 + 每题对错 |

### 8.2 关键交互

- **排版面板实时驱动**：6 个参数写入 CSS 变量（`--cols-per-row`、`--row-gap`、`--font-size`、`--page-margin`、`--answer-line`、`--header-bar`），预览区用 `transform: scale()` 模拟 A4，无需往返服务端。
- **学生端一屏一题**（D22）：全屏卡片切换 + 题目进度条；`inputmode="numeric"` 拉起数字键盘；提交前校验未答题。
- **两端不共享代码**：学生端打包产物不含老师端组件，减少手机上加载体积。

## 9. 渲染与导出

### 9.1 单一 HTML 真相源

```
LayoutParams + Question[]  →  Jinja2 模板  →  sheet.html
                                                 │
                     ┌───────────────────────────┼───────────────────────────┐
                     ▼                           ▼                           ▼
              浏览器预览/打印              Playwright → PDF            python-docx → Word
              (window.print)              (同一 HTML)                 (独立渲染)
```

**PDF 与打印完全一致**，因为它们用的是同一份 HTML 与同一套 CSS。这是选 Playwright 的核心理由。

**Word 是例外**：`.docx` 的排版模型（段落 / 表格 / 分节）与 CSS 流式排版不同，**不可能像素级一致**。设计上明确界定为：

| 面向 | 一致性要求 |
| --- | --- |
| 预览 / 打印 / PDF | **像素级一致**（同一 HTML） |
| Word | **结构一致**：相同的题号、题目内容、每行题数（用表格行实现）、答题空位；字号与页边距按参数映射到磅值，允许细微差异 |

这条边界要写进老师端界面（导出 Word 旁的小字说明），避免老师期待落空。**已确认为 D33**。

### 9.2 A4 常量

```
A4 = 210mm × 297mm
@page { size: A4; margin: var(--page-margin); }
```

**分页保护**（NFR-5）：题目块设 `break-inside: avoid`，行容器设 `break-inside: avoid`；渲染后由 Playwright 校验页数，若某题块被切分则回溯调整行间距（自动微调，或在界面提示老师「建议减小字号」）。

## 10. 部署与运行

```
# 单条命令启动（老师机器）
mathgen serve --port 8000
  ├─ 初始化 data/ 与 SQLite（首次运行自动建表）
  ├─ 探测局域网 IP（枚举网卡，排除回环与虚拟网卡）
  ├─ 打印： 老师端 http://192.168.x.x:8000/teacher
  │         学生端 http://192.168.x.x:8000/student
  ├─ 终端打印 ASCII 二维码 / 也可在老师端页面显示
  └─ uvicorn 绑定 0.0.0.0:8000
```

| 项 | 方案 |
| --- | --- |
| 依赖分发 | `uv` 管理虚拟环境与依赖（本机已有 uv 工作流） |

| 数据目录 | `mathgen/data/`（DB + 导出文件），备份即复制 |
| 离线 | 前端资源与字体全部本地打包，无 CDN（NFR-9） |

## 11. 性能与并发

| 场景 | 设计 |
| --- | --- |
| 生成 20–50 题 | 纯内存构造，实测目标 < 100ms，远低于 NFR-4 的 1s |
| 数十名学生并发提交 | SQLite **WAL 模式** + 短事务；判分不落重计算 |
| 导出 PDF | Playwright 启动开销约数百 ms，采用**常驻浏览器实例**复用 |
| 卷库读取 | 读快照，不重算；`paper_item` 走 `(paper_id, seq)` 唯一索引 |

**并发风险点**：数十名学生同时提交时 SQLite 写入串行化。缓解：WAL + 每次提交一个短事务；若实测出现 `database is locked`，降级方案是提交入内存队列后批量落库（登记为 DQ8 的兜底）。

## 12. 安全与隐私

| 项 | 设计 |
| --- | --- |
| 鉴权 | **不做**（D5 个人自用 + NFR-1 局域网）。风险：同局域网任何人可访问老师端。缓解：启动时终端明示「请勿在公共 Wi-Fi 使用」；提供 `--token` 可选参数做简单口令保护（默认关闭） |
| 答案泄露 | 学生端接口剔除 `answer` / `steps`（§7.2），加自动化测试 |
| 个人信息 | 只存姓名、学号与作答（NFR-3 / D35），无手机号 / 设备号 |
| 数据出境 | 无任何外部请求；字体、二维码全部本地生成 |
