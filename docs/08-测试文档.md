## 1. 测试概述

### 1.1 目的与范围

本文档记录**已经实现并已验收的系统**的测试工作：测了什么、怎么测、测出什么、还有什么没测。它不写「打算怎么测」——那是 `docs/06` 在 M1 之前就冻结下来的门禁设计。

范围边界三条：

- **被测**：出题引擎、判分、排版与卷面渲染、导出（PDF / Word / 成绩 CSV·Excel）、后端 API、老师端界面、学生端界面，以及 NFR-4（并发）、NFR-5（打印保真）、NFR-9（离线）三项非功能需求。
- **不测**：本期范围之外的功能——FR-S9 错题本（D25）、FR-E13 竖式（D24）、FR-E14 文字应用题（D31）、FR-E15 小数与分数（D9）、FR-L 手写批改与后期竖式。
- **无法测或未覆盖**：需要物理设备才能验的部分（真实打印机 / 打印驱动），以及只有真用户能覆盖的部分（教师自定义内容）。完整的未覆盖清单见 §8.2。

### 1.4 术语

| 术语 | 含义 |
| --- | --- |
| 门禁 | 一条可复现命令加一组断言；红了就不许提交（`docs/03` §6） |
| 判据 | 门禁里的单条断言，必须能在被违反时**真的变红** |
| 负对照 | 故意制造违反条件、证明判据会红的对照实验（`docs/03` V9） |
| 哈希夹逼 | 在门禁运行窗口前后各算一次源码聚合哈希，逐字节相同才承认这次运行有效（V8） |
| 假绿 | 门禁绿了，但绿的理由不是「被测行为正确」——本项目最重视的失效模式 |
| 独立验收 | 由**未参与该功能实现**的成员另写判据复核，不接受实现方自证 |

## 2. 测试计划

### 2.1 分层策略

测试按「离被测行为有多近」分层：越靠下的层越快、越容易定位，越靠上的层越接近真实使用、越能发现「每个部件都对、合起来不对」的问题。分层与规模见下图。

| 层 | 范围 | 工具 | 运行时机 |
| --- | --- | --- | --- |
| L1 单元 | 引擎出题、判分、排版容量模型（纯逻辑，不碰数据库与网络） | unittest（标准库，零依赖） | 每次改动 |
| L2 契约 | 数据结构字段、API 出入参、依赖方向、冻结契约哈希、源文件文本卫生 | unittest + sha256 守卫 | 每次改动 |
| L3 安全 | 学生端取题响应不得含 `answer` / `steps`（契约 §9 冻结） | unittest + 响应体逐键断言 | 每次改动 |
| L4 渲染 | 卷面 HTML、A4 分页、页边距、NFR-5 排版容量守卫 | Playwright + Chromium | 模块完成时 |
| L5 端到端 | 老师出卷→打印；学生扫码→作答→判分→成绩 | Playwright + 真机双档 | 里程碑验收 |
| L6 性能 | 生成耗时、并发提交不阻塞 | unittest + 时延统计 | M6 |
| FE 前端门禁 | 界面与构建产物（12 步，fail-fast） | node 脚本 + Playwright | 每次前端改动 |

> **为什么用标准库 `unittest` 而不是 pytest**（D43）：本机 pip 不可用、运行时也没有预装 pytest，测试一律写成 `unittest.TestCase` 子类，保证「克隆下来就能跑」。
>
> **为什么把契约与功能测试分开**（P4）：契约测试守的是「冻结的结构不许变」，一旦它红了，功能测试的结果就不可信——所以要能分开跑、分开判。

### 2.2 各层门禁与命令

前端门禁是一条 fail-fast 链：**先**跑 1 项前置判据与 2 项前置自检，再依次跑 12 个脚本，任一失败即整体失败，退出码 1 表示门禁未过、2 表示用法或前置错误。

| 步骤 | 脚本 | 判据 |
| --- | --- | --- |
| 前置 | `scripts/dist-freshness.mjs` | `frontend/dist` 必须比它的构建输入新（陈旧产物＝浏览器门禁测的是旧 bundle） |
| 前置 | `scripts/check-script-syntax.mjs` | 逐个 `node --check` `frontend/scripts/*.mjs`（含正负对照） |
| 前置 | `scripts/fix-inline-python-backticks.mjs --self-test` | 反引号整洁工具自身的自检 |
| ① | `verify-no-cdn.mjs` | 产物无外部资源引用（位置感知：只看 `src=` / `href=` / `url()` / `@import` / `fetch(`） |
| ② | `verify-contract.py` | 前端类型 ↔ `backend/app/contracts/{api,layout}.py` |
| ③ | `verify-layout-css-vars.mjs` | 排版面板六控件实时驱动预览区 CSS 变量 |
| ④ | `verify-teacher-ui.mjs` | 六维表单 / 打印版式 / 后端未就绪降级 |
| ⑤ | `verify-library-m3.mjs` | M3 卷库（分页 / 搜索 / 筛选 / 按卷号）与第六维落库 |
| ⑥ | `verify-tokens.mjs` | 判据 A1：令牌之外没有颜色字面量 |
| ⑦ | `verify-structure.mjs` | 判据 A2/A3/A4/A7/A8：组件状态与骨架几何 |
| ⑧ | `verify-preview-scale.mjs` | A9：预览是打印几何的等比缩小（进 iframe 量纸内几何） |
| ⑨ | `verify-ui-voice.mjs` | A10/A11：无开发者文本、灰底只用于画布 |
| ⑩ | `verify-negative-controls.mjs` | 负对照（V9）：故意弄红，证明上述判据能失败 |
| ⑪ | `verify-ui-voice.mjs --self-test` | 门禁⑨自带负对照：覆盖面注入对照 + 身份预置承重 |
| ⑫ | `compare-mock-and-real.mjs` | mock ↔ 真实后端逐字段比对（结构 / 状态码 / D74 方向） |

### 3.5 两个已实测的环境坑

**坑 1 · Playwright 启动会连撞两个成因不同的 EPERM。** 两个都要解决才能出 PDF：一是浏览器安装目录锁定（`__dirlock`）失败，绕过方式是把浏览器装进仓库并设置 `PLAYWRIGHT_BROWSERS_PATH`；二是 `mkdtemp` 失败，绕过方式是把 `TEMP` / `TMP` 指向仓库内目录。**同一个 `mkdtemp` 坑也命中 LibreOffice Kit**——它的转换子进程若用系统 `TEMP` 会报 `EPERM`。两个坑都实测验过：Chromium 156.0.8078.4 可正常启动并渲染。

**坑 2 · LibreOffice 光栅后端（docx → PNG）会把版心放大。** 同一份 docx，走 `render` 出图时墨迹落在 x ∈ [3.60, 20.99] cm（看起来像内容被顶出右页边距），而走 `convert` 出 PDF 时文字在 x ∈ [2.40, 17.78] cm，左右留白正常；同一份 PDF 再用 kit 的 `render` 转 PNG，量到的墨迹仍是 x ∈ [2.38, 18.61] cm。**结论：缺陷在 LibreOffice 光栅后端，不在文档，也不在 pdfium 通道。**

| 通道 | 版心左边界（设定边距 2.4cm 的文档） | 判定 |
| --- | --- | --- |
| docx → PNG（LibreOffice 光栅） | 3.60 cm | 不合格 |
| docx → PDF → PNG（pdfium） | 2.38 cm | 合格（≈ 设定值） |
| docx → PDF（文字矩阵锚点） | 2.40 cm | 合格 |

> **因此版式验收一律走 `convert` 成 PDF 再判**，不要用 docx → PNG 判断版式。这条在 M3 就被记为环境坑写进了 `AGENTS.md`；本文档编写时用一次性探针重新量了一遍（探针按惯例不入库，量测方法与两次实测数字见 §3.5 与 §6.2 的 BG-45）。

## 6. 缺陷记录

### 6.1 分类规则

缺陷按**性质**分五类，规则如下：

| 性质 | 判定标准 |
| --- | --- |
| 真实缺陷 | 用户可见的行为不符合需求或健壮性不足；**产出交付物的工具链也算**——文档构建脚本把交付文档的内容搞丢，与产品缺陷同等对待（BG-46） |
| 契约漂移 | 冻结契约 / 设计文档 / 规格措辞与实现不一致，或规范本身未定义、不可判定 |
| 门禁 / 测试设施故障 | 判据本身坏了：恒真、恒红、打错目标、覆盖面没扫到它声称的对象 |
| 验证方假阳性 | 验证工具或测量方法把正确的东西判成错的（或反之），产品没错 |
| 环境 / 流程 | 工具链与协作时序造成的问题，产品代码无关 |

**发现阶段**记的是「缺陷被发现的里程碑」，不是「被引入的里程碑」——M6 期间发现的可能是 M2 埋下的。**出处**一列给出仓库内可复查的位置（文件加行号或表名）；每条缺陷都有回归判据，回归判据一列同时给出自动化归属。

## 8. 测试结论与遗留问题

### 8.1 结论

1. **功能**：M1–M6 全部里程碑经用户确认验收；41 条功能需求中，本期范围内的全部通过，范围外的 4 条明确不适用。
2. **非功能**：NFR-1、NFR-2、NFR-3、NFR-4、NFR-7、NFR-8、NFR-9 全部通过；NFR-5 通过但有明确限定；NFR-6 通过但微信内置浏览器只覆盖了可自动化的一小部分（Tier 2 明标 UNVERIFIED）。
3. **质量**：全量后端 1254 用例、前端 12 步门禁全绿，且每次权威跑都有源码哈希夹逼证明「结论对应的是这份代码」。
4. **缺陷**：47 条，全部闭环或有明确处置；分布上「文档与实现漂移」与「真实缺陷」并列最多（各 15 条，32%），说明本项目的风险重心不在算法而在**一致性**，后续应以机器对账为主要手段。
5. **判据本身的质量**：11 条缺陷属于「判据坏了」（恒真 / 恒红 / 打错目标 / 覆盖面失真）。这不是测试做得差，而是把判据当一等公民来验的结果——**先怀疑自己的判据，再怀疑产品**。
